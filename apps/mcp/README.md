# @jaw-mono/mcp

The hosted JAW MCP server. Any MCP client connects over Streamable HTTP at `/mcp` and authorizes through OAuth 2.1. The account owner approves the connection once, in the JAW wallet, the same way `jaw session setup` does for the CLI: a daily USDC budget granted on chain to a session key the server holds. The budget is USDC only: within it the agent pays x402 services with no further prompts. A USDC transfer or any other contract call goes to the owner, who approves it in the wallet each time and pays its gas.

## Connecting

`/oauth/authorize` lands on `/interaction/<uid>`, a page this server renders. When the owner clicks "Open JAW", it opens a session on JAW's relay and links the owner to keys.jaw.id `/cli-bridge`, the page the CLI uses, so every request is answered in the wallet's own dialogs. Messages over the relay are encrypted end to end under a key agreed through the link's fragment, and carry no key of this server: the page uses its own deployment's.

A CIMD client must include `refresh_token` in its `grant_types`, or the server refuses it with `invalid_client_metadata` before any consent screen. Without a refresh token the session key lives only in the short access token, and the float granted at connect would be stranded once it expires.

A CIMD client must also be public: `token_endpoint_auth_method` `none` and no `jwks_uri`, since a `jwks_uri` is fetched on every token request the client signs. ChatGPT, whose document at `https://chatgpt.com/oauth/client.json` signs with `private_key_jwt`, is the one exception: a document served from the `https://chatgpt.com` origin may use `private_key_jwt`, and only with the `jwks_uri` `https://chatgpt.com/oauth/jwks.json`. Codex connects through the same client.

The owner first signs a plain-text sign-in that names the app, the domain of its metadata document, what it asks for, and a six-character code the page also shows. The wallet link can be forwarded, so the text asks the owner to approve only if the page that sent them there shows that code. A connection that spends then asks for the budget, and its permission must come from the account that signed in; the server checks it on chain. The page completes the authorization once the server has both.

The session key is created once the owner signs in, and stored sealed before the wallet is asked for the budget, since the grant's prefund goes to its address. A retry of the same interaction keeps that key. The sealed copy stays until the code exchange, which wraps it under the refresh token and clears it. If the code exchange never happens (the client drops the authorization code, or the provider fails to hand it back), the reconciler retires the connection once the exchange window passes (the code TTL of 60 seconds plus a two-minute margin): it revokes the on-chain budget, returns the prefund to the owner, clears the sealed key and ends the connection. A retire that cannot run (payments paused, no API key, chain error) keeps the key and logs at error level for the next run. The ticket and the code are derived from the interaction under the sealing key, so every replica shows the same ones.

A wallet session ends at a deadline: a minute before the thirty-minute interaction ends, or thirty minutes after a grant, revoke, sign or `jaw_send_calls` request. An approval cannot land after the flow it belongs to is over. While a session waits, the server sends the relay a ping every five minutes, since the relay ends a session after fifteen minutes with no message. An authorization session that no browser joins within ten minutes ends and gives its slot back, and clicking Open JAW again on the same page opens a new one. Sessions for the tools wait the whole thirty minutes, since the owner opens those links from a chat, often later, and nothing would hand them a new one. One process holds at most 150 sessions for authorizations and 50 for `jaw_grant_permissions`, `jaw_revoke_permission`, `jaw_sign`, `jaw_send_calls` and `jaw_swap`, so authorizations cannot take the slots the tools need; past either, the page or the tool answers that the wallet is busy. A session opens only on the owner's click, from the browser holding the interaction cookie, and one address can hold 5 of them at a time and one client 50. Holding them needs a long-lived Node process, as the Docker image runs, not serverless functions.

One account can hold at most 20 active connections. The check runs after the owner signs in, before the budget is asked, so no session key or prefund is created for a connection that would exceed the cap. The page tells the owner to disconnect one from its app (`jaw_session_disconnect` called from that app ends it) or wait for one to expire. `jaw_connections` lists them, and `jaw_revoke_permission` removes their grants.

## Scopes

| Scope                                 | Tools                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wallet:read` (required, the default) | `jaw_session_status`, `jaw_session_x402_discover`, `jaw_session_x402_quote`, `jaw_add_funds`, `jaw_session_history`, `jaw_connections`, `jaw_revoke_permission`, `jaw_session_disconnect`, `jaw_swap_status`, `jaw_send_calls`, `jaw_get_calls_status`, `jaw_get_assets`, `jaw_get_calls_history`, `jaw_get_permissions`, `jaw_get_capabilities`, `jaw_read_contracts`, `jaw_sign` |
| `x402:pay`                            | `jaw_grant_permissions`, `jaw_session_x402_pay`, `jaw_swap`, `jaw_session_execute`                                                                                                                                                                                                                                                                                                 |

No scope implies another. A tool refused for a missing scope answers with an error naming the scope; the agent reconnects and asks for it, which makes a new connection, so a budget approved on the old one does not carry over.

A payment past what the budget has left is refused and points at `jaw_grant_permissions`, whose `x402Budget` preset returns a wallet link for the owner to approve a new daily USDC budget. The same tool takes `calls`, target and function signature pairs, and `spends`, a token, an allowance in base units, a period from `minute` to `forever` and a multiplier, for a custom grant the session key holds instead. A grant ends at `expiresAt` or with the connection, whichever comes first, an expiry already past is refused as `expiry_in_past` and one inside the 30 minutes the owner has to approve as `expiry_too_soon`, and a call to the account, the permission manager, an EntryPoint or the any-contract wildcard is refused as `call_target_refused`. A connection can hold up to 5 live grants of either kind, and `jaw_grant_permissions` refuses before it opens a wallet link once it does. Payments, quotes, swaps and refills draw from the newest x402 budget that is still live, never from a custom grant, and an older grant stays approved until it expires or `jaw_session_disconnect` revokes every live grant of the connection with the float return. Other contract calls stay outside the budget. `jaw_send_calls` asks the owner to approve up to 10 calls on one chain: it returns a wallet link, and the owner reviews and signs them in the wallet and pays the gas. `jaw_get_calls_status` follows the request until it is mined. `jaw_sign` asks the owner to sign a message (EIP-191) or EIP-712 typed data: it returns a wallet link, and the same call with the same `idempotencyKey` returns the signature once the owner approves. A connection waits on one sign link at a time. A session key never signs for the account.

`jaw_read_contracts` batches view-function reads (up to 100) on any chain JAW supports, through the JAW RPC proxy, and returns each decoded value or its own error.

`jaw_session_execute` sends up to 10 calls as the session key under a custom grant, by its `permissionId`, with no prompt to the owner, on a connection granted `x402:pay`. Before any userOp it checks every call's target and function against the grant, the `0x3232...3232` and `0x32323232` wildcards included, then reads from the chain whether the grant still stands and what each spend limit has left this period, less what earlier runs still open hold. It refuses by name: `call-not-allowed`, `over-limit`, `expired` or `no-grant`, and the x402 budget is refused as `no-grant` since it pays x402 services only. An `approve` or `transferFrom` on a contract the grant sets no limit on is left to the chain, since the manager skips those on an ERC-721. The same names come back when the permission manager refuses a batch that passed those checks, read from the revert data of a failed simulation or from the EntryPoint's revert log. A run takes the connection's float lock while it is checked, recorded and submitted, and its rows count against later runs until they settle, so of two runs that together pass a limit the second refuses. A send whose answer was lost on the way back is reported as possibly sent and keeps its rows open. Each run is a row in `sends` per token it moves, under its `idempotencyKey`: the same key with the same calls returns that run's outcome and never sends twice, and the same key with other calls is refused as `idempotency_conflict`. A key never runs twice: after a run that sent nothing, a new key sends again. `jaw_session_history` lists the rows with their userOp hash, and the reconciler settles a run that got no receipt in time by that hash alone, since refills and other runs share its sender. A run whose answer was lost has no hash, so the reconciler never marks it landed and releases it once its block window passes. A released run keeps the transaction it reverted in, so its key replays a revert apart from a run never seen on chain. The fee comes from the session key's USDC, which an x402 budget funds, and `payments_paused` stops it before anything is sent.

`jaw_session_x402_discover` searches the x402 Bazaar for services payable on the connection's chain, as the CLI's does; resolving a name is one of those services, not a free tool.

## Run it

```bash
docker build -f apps/mcp/Dockerfile -t jaw-mcp .   # from the repository root
docker run -p 3000:3000 -e DATABASE_URL=... -e JAW_MCP_PUBLIC_URL=http://localhost:3000 \
  -e JAW_KEYS_URL=https://keys.jaw.id -e JAW_MCP_SEALING_KEYS=... jaw-mcp
```

Migrations run at start and are safe to run from several instances at once.

Migrations must run as the app role, over a direct connection to Postgres, not through a transaction-mode pooler such as PgBouncer or the Supabase pooler on port 6543. Migration `0011` sets `statement_timeout` for the current role in the current database, so a different role leaves the app database unbounded. The runner also relies on session state, `set statement_timeout = 0` and `pg_advisory_lock`, which a transaction-mode pooler can move to another backend between statements, so the lock and the timeout reset stop holding. `GET /api/health` answers `{ db, paused }`, and 503 when Postgres is unreachable.

Each instance opens up to 26 Postgres sessions: a pool of 10 for requests, plus one session per refill or disconnect in progress, at most 16, which holds that connection's funding lock while it waits on the chain. Size `max_connections`, or the pooler in front of Postgres, for 26 per instance.

## Tests

`bunx nx test @jaw-mono/mcp` runs on PGlite, which runs one transaction at a time, so it cannot show a lock race. `test-pg` runs every `*.test.ts` file under `src` that references `TEST_PG_URL` (`beforeAll(TEST_PG_URL ? useTestPostgres : useTestDb)`), so a new file opts in by importing it on a real Postgres, one fresh database per file, plus the tests under `describe.skipIf(!TEST_PG_URL)`. CI runs it against a `postgres:17` service. Locally:

```bash
docker run -d --rm --name mcp-test-pg -e POSTGRES_PASSWORD=pg -p 55432:5432 postgres:17
MCP_TEST_DATABASE_URL=postgres://postgres:pg@127.0.0.1:55432/postgres bunx nx run @jaw-mono/mcp:test-pg
```

A killed run can leave `mcp_test_*` databases behind. List them with `psql "$MCP_TEST_DATABASE_URL" -c '\l mcp_test_*'` and drop each with `drop database <name> with (force)`. Removing the container removes them all.

## Configuration

| Variable                       | Required | Meaning                                                                                                                                                                                |
| ------------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                 | yes      | Postgres connection string                                                                                                                                                             |
| `JAW_MCP_PUBLIC_URL`           | yes      | The origin clients reach. It is the OAuth issuer, and the MCP resource is `<origin>/mcp`                                                                                               |
| `JAW_KEYS_URL`                 | yes      | The keys.jaw.id origin whose `/cli-bridge` page the owner opens to approve                                                                                                             |
| `JAW_RELAY_URL`                | no       | The relay that page and this server talk through, `wss://relay.jaw.id` by default                                                                                                      |
| `JAW_MCP_DAILY_BUDGET`         | no       | USDC base units per day a paying connection asks for when it connects, default 1000000 (1 USDC). `jaw_grant_permissions` asks for another                                              |
| `JAW_MCP_SEALING_KEYS`         | yes      | Comma-separated base64url keys of 32 bytes, newest first. New tokens use the first; any of them opens an existing one                                                                  |
| `JAW_MCP_CHAIN_ID`             | no       | 84532 (default) or 8453                                                                                                                                                                |
| `JAW_MCP_RPC_URL`              | no       | RPC for that chain; the chain's public RPC when unset                                                                                                                                  |
| `JAW_MCP_MAINNET_RPC_URL`      | no       | RPC for ENS lookups                                                                                                                                                                    |
| `JAW_MCP_TRUSTED_PROXY_HOPS`   | no       | Proxies in front that append to `x-forwarded-for`. Unset or 0 ignores that header and rate-limits on `x-real-ip`, which Vercel sets itself                                             |
| `JAW_MCP_INSECURE_FETCH_HOSTS` | no       | `host:port` list `jaw_session_x402_quote` and `jaw_session_x402_pay` may reach over http or a private address. Startup fails unless `JAW_MCP_PUBLIC_URL` is local                      |
| `JAW_MCP_SWAP_URL`             | no       | Base URL of the swap backend, `https://api.justaname.id/proxy/v2` by default. No query or hash, and https to a public host unless its `host:port` is in `JAW_MCP_INSECURE_FETCH_HOSTS` |
| `JAW_MCP_SWAP_QUOTE_TTL_SEC`   | no       | Seconds the swap backend keeps a quote, its `AURORA_QUOTE_TTL_SEC`, default 300. The owner has until 60 s before that, thirty minutes at most, to approve a `jaw_swap` deposit         |
| `JAW_MCP_API_KEY`              | no       | JAW api key the ERC-20 paymaster charges a refill's gas through. Unset, no refill runs and a payer with no float cannot pay                                                            |
| `JAW_MCP_FLOAT_TARGET`         | no       | Base units a refill brings the payer up to, default 250000 (0.25 USDC), so most payments need no refill. The budget's daily cap still bounds every refill                              |
| `JAW_MCP_CRON_SECRET`          | no       | Bearer secret for `/api/cron/reconcile` and `/api/metrics`. Unset, both answer 401                                                                                                     |
| `JAW_MCP_RECONCILE_EVERY`      | no       | Seconds between reconciler runs inside the server, default 60. Set 0 only when a cron calls `/api/cron/reconcile`                                                                      |

A connection's expiry slides forward by 30 days on every successful token refresh, so a client in active use never hits the cliff. A client that stops refreshing expires after 30 days of inactivity. `jaw_session_status` includes `connectionExpiresAt` and warns the agent when the connection is within 48 hours of expiry, so it can call `jaw_session_disconnect` to sweep the float and revoke budgets while it still holds a working token. When a reused refresh token triggers revocation and its key wrap is still present (before the periodic sweep), the server recovers the key and sweeps the float before ending the connection.

To rotate sealing keys, put the new key first. A connection moves to the new key on its next token refresh, so keep the old key for at least 30 days (the maximum idle lifetime) before dropping it; `select split_part(key_wrap, '.', 2), count(*) from oauth_payloads where model = 'RefreshToken' and consumed_at is null group by 1` shows which keys are still in use. A refresh that needs a dropped key fails without using up the token, so restoring the key repairs it. Generate a key with `openssl rand -base64 32 | tr '+/' '-_' | tr -d '='`.

## Operations

The kill switch stops `/mcp`, OAuth and the interaction routes with a 503 and leaves health up:

```sql
insert into settings (key, value) values ('paused', 'true')
on conflict (key) do update set value = excluded.value, updated_at = now();
```

Payments alone stop with `('payments_paused', 'true')` in the same table: `jaw_session_x402_pay` and `jaw_swap` refuse with `payments_paused` before they sign anything (a `jaw_swap` retry of a stored swap still answers), `jaw_send_calls` refuses before it opens a wallet link (a retry whose link is still live answers from the stored request), `jaw_get_calls_status` keeps working, `jaw_session_disconnect` refuses before it revokes or returns anything, and every other tool keeps working.

`/api/cron/reconcile` (GET or POST, `Authorization: Bearer <JAW_MCP_CRON_SECRET>`) clears the key wraps of refresh tokens used more than a minute ago, settles or fails every payment left `signed` or `unknown` for more than a minute by asking the chain, logs one error per payment still unanswered an hour past its deadline, concludes up to 50 `jaw_send_calls` requests left `sent` for more than a minute as `landed` or `reverted` by reading the bundler receipt (a request still at `send_started` has no calls id to read and is left alone; the bundler answers only for recent user operations, so one it has no receipt for ten minutes after the send is looked up on chain instead, as the `UserOperationEvent` of EntryPoint 0.8 for its calls id, in ranges of 200 blocks (the cap of the public Base RPC) and at most 50 ranges per request, for at most 5 requests per run and none once the head is 10,000 blocks past where the search starts, from the head recorded when it was sent or, for older rows, from a block estimated from the row's age; `jaw_get_calls_status` does the same), and deletes expired OAuth state, rate limit windows, audit events older than 90 days, and pending connections nothing refers to. A pending connection the owner approved but whose authorization never completed is retired past the interaction's end: its key revokes the budget and returns the prefund to the owner, as `jaw_session_disconnect` does, and then its sealed key is cleared. A run that cannot send keeps the key for the next one. `/api/metrics` serves payments by state, the reconciler backlog, refused `/mcp` calls per client, and `jaw_mcp_wraps_past_window`, the key wraps still stored for refresh tokens past their retry window, in Prometheus text. Each rotation sweeps those wraps and logs `wrap sweep failed` when it cannot; alert when the gauge stays above zero for longer than one cron interval.

Every tool call writes one row to `audit_events` with the connection, the tool, the outcome, and the request id from `x-request-id`. The outcome is `ok`, `error`, the code of a payment that ended without paying (such as `budget_exhausted` or `payments_paused`), or `unknown` for a payment that may have reached the seller while the chain settles it. Arguments and results are never stored. `jaw_connections` lists every connection of the account with the grants it holds by `permissionId`: kind, spend limits, expiry, and whether each is live, expired or revoked. `jaw_revoke_permission` asks the owner to revoke one permission on chain with `wallet_revokePermissions`, which the wallet renders from JAW's permission store and the owner pays the gas for. It takes any permission granted from the account: this connection's, another connection's, or one approved on chain that this server never recorded, which it reads from the same store. The tool refuses an unknown id, a chain the permission was not granted on, a permission already revoked or ended, and a recorded grant the store does not hold, before any link opens. One connection waits on one revoke at a time, and a permission has one revoke link across the account; unique indexes on `permission_requests` hold both. Once the chain shows it revoked, the `grants` row is marked revoked. A grant the wallet answered but the server did not record keeps its id on the request row, and `jaw_connections` lists it under `unrecorded` until a revoke of it is confirmed on chain. Grant, revoke and `jaw_sign` links are rows in `permission_requests` and count toward the account's three open links with `jaw_send_calls` and `jaw_swap`. A row whose process stopped renewing its lease no longer counts. The relay drops what the wallet sends while no process listens on its link, so a restarted server cannot hear an answer given there. If that session had not asked the wallet yet, the next request for the same thing marks the row expired with `session_lost` and opens a new link. If it had, or if the relay session dropped after asking, the row ends expired with `link_lost`. `jaw_sign` answers `link_lost` for that key. The next new link of the same kind (grant, revoke or sign) from the same connection names the lost one, and only that link does: its replies, retries included, carry the warning while the owner could still approve the old link, so the agent can tell the owner not to. Once a link is `link_lost` the owner holds two links for the same kind of request. The server never hears an answer on the old one, but a grant or revoke the owner approves there still happens on chain, which is why the warning asks the owner not to. A database stall long enough to lapse the lease of a process that still runs is the one case where the server can hear both: the old process keeps its socket, and an answer it hears there still settles the old row, until its first lease renewal that the database answers finds the row closed and drops the socket. That is within 10 seconds of the database answering again. After a real restart no process listens on the old link, and the relay drops what the wallet sends there. A connection never closes another connection's asked revoke before its window ends: a revoke of the same permission from another connection gets `revoke_in_progress` while that link is live or asked, even after its lease lapsed. A link whose lease lapsed before it asked the owner can never ask, so any connection may close it as `session_lost`. Before asking the wallet, a session claims its row while the lease holds, so a session that lost its row never asks. `jaw_session_disconnect`, called from the connection itself, also revokes its budgets on chain and returns the float to the owner first. When the payer's balance is too low to cover both the fee and a sweep, a revoke-only batch sends the revocations and lets the paymaster take its fee from whatever is there; the remainder stays in the payer. A grant whose state the chain does not return is left out of the batch and listed in `unread`, and the rest still revoke and sweep.

Authenticated `/mcp` calls get 120 requests per minute per connection, and unauthenticated routes 120 per client IP, counted in Postgres. Behind your own proxy, production must set `JAW_MCP_TRUSTED_PROXY_HOPS`: without it the client IP comes only from `x-real-ip` (which Vercel sets), and with neither the per-IP limit is skipped rather than shared, with a warning at start. See `.env.example`.
