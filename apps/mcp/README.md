# @jaw-mono/mcp

The hosted JAW MCP server. Any MCP client connects over Streamable HTTP at `/mcp` and authorizes through OAuth 2.1. The account owner connects by signing in with the JAW wallet and signing a message, and can use the connection right away. The server holds a session key for it. The first time the agent needs to pay, it asks the owner for a daily USDC budget with `jaw_grant_permissions`, granted on chain to that key. The budget is USDC only: within it the agent pays x402 services with no further prompts. A USDC transfer or any other contract call goes to the owner, who approves it in the wallet each time and pays its gas.

## Connecting

`/oauth/authorize` lands on `/interaction/<uid>`, a page this server renders. When the owner clicks "Open JAW", it opens a session on JAW's relay and links the owner to keys.jaw.id `/cli-bridge`, the page the CLI uses, so every request is answered in the wallet's own dialogs. Messages over the relay are encrypted end to end under a key agreed through the link's fragment, and carry no key of this server: the page uses its own deployment's.

A CIMD client must include `refresh_token` in its `grant_types`, or the server refuses it with `invalid_client_metadata` before any consent screen. Without a refresh token the session key lives only in the short access token, and the float a budget grants would be stranded once it expires.

A CIMD client must also be public: `token_endpoint_auth_method` `none` and no `jwks_uri`, since a `jwks_uri` is fetched on every token request the client signs. ChatGPT, whose document at `https://chatgpt.com/oauth/client.json` signs with `private_key_jwt`, is the one exception: a document served from the `https://chatgpt.com` origin may use `private_key_jwt`, and only with the `jwks_uri` `https://chatgpt.com/oauth/jwks.json`. Codex connects through the same client.

The owner first signs a plain-text sign-in that names the app, the domain of its metadata document, what it asks for, and a six-character code the page also shows. The wallet link can be forwarded, so the text asks the owner to approve only if the page that sent them there shows that code. No budget is asked for here. The page completes the authorization once the server has the signature.

The session key is created once the owner signs in, and stored sealed, since a budget granted later prefunds its address. A retry of the same interaction keeps that key. The sealed copy stays until the code exchange, which wraps it under the refresh token and clears it. If the code exchange never happens (the client drops the authorization code, or the provider fails to hand it back), the reconciler retires the connection once the exchange window passes (the code TTL of 60 seconds plus a two-minute margin): it revokes any on-chain budget, returns any prefund to the owner, clears the sealed key and ends the connection. A retire that cannot run (payments paused, no API key, chain error) keeps the key and logs at error level for the next run. The ticket and the code are derived from the interaction under the sealing key, so every replica shows the same ones.

A wallet session ends at a deadline: a minute before the thirty-minute interaction ends, or thirty minutes after a grant, revoke, sign, add funds or `jaw_send_calls` request. An approval cannot land after the flow it belongs to is over. While a session waits, the server sends the relay a ping every five minutes, since the relay ends a session after fifteen minutes with no message. An authorization session that no browser joins within ten minutes ends and gives its slot back, and clicking Open JAW again on the same page opens a new one. Sessions for the tools wait the whole thirty minutes, since the owner opens those links from a chat, often later, and nothing would hand them a new one. One process holds at most 150 sessions for authorizations and 50 for `jaw_grant_permissions`, `jaw_revoke_permission`, `jaw_sign`, `jaw_add_funds`, `jaw_send_calls` and `jaw_swap`, so authorizations cannot take the slots the tools need; past either, the page or the tool answers that the wallet is busy. A session opens only on the owner's click, from the browser holding the interaction cookie, and one address can hold 5 of them at a time and one client 50. Holding them needs a long-lived Node process, as the Docker image runs, not serverless functions.

One account can hold at most 20 active connections. The check runs after the owner signs in, so no session key is created for a connection that would exceed the cap. The page tells the owner to disconnect one from its app (`jaw_session_disconnect` called from that app ends it) or wait for one to expire. `jaw_connections` lists them, and `jaw_revoke_permission` removes their grants.

## Scopes

| Scope                                 | Tools                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wallet:read` (required, the default) | `jaw_session_status`, `jaw_session_x402_discover`, `jaw_session_x402_quote`, `jaw_add_funds`, `jaw_session_history`, `jaw_connections`, `jaw_revoke_permission`, `jaw_session_disconnect`, `jaw_swap`, `jaw_swap_status`, `jaw_send_calls`, `jaw_get_calls_status`, `jaw_get_sign_status`, `jaw_get_grant_status`, `jaw_get_assets`, `jaw_get_defi_positions`, `jaw_get_calls_history`, `jaw_get_permissions`, `jaw_get_capabilities`, `jaw_read_contracts`, `jaw_simulate_calls`, `jaw_resolve_name`, `jaw_sign` |
| `x402:pay`                            | `jaw_grant_permissions`, `jaw_session_x402_pay`, `jaw_session_execute`                                                                                                                                                                                                                                                                                                                                                                                                                                            |

No scope implies another. A tool refused for a missing scope answers with an error naming the scope; the agent reconnects and asks for it, which makes a new connection, so a budget approved on the old one does not carry over.

A payment past what the budget has left is refused and points at `jaw_grant_permissions`, whose `x402Budget` preset returns a wallet link for the owner to approve a new daily USDC budget. The same tool takes `calls`, target and function signature pairs, and `spends`, a token, an allowance in base units, a period from `minute` to `forever` and a multiplier, for a custom grant the session key holds instead. A grant ends at `expiresAt` or with the connection, whichever comes first, an expiry already past is refused as `expiry_in_past` and one inside the 30 minutes the owner has to approve as `expiry_too_soon`, and a call to the account, the permission manager, an EntryPoint or the any-contract wildcard is refused as `call_target_refused`. A connection can hold up to 5 live grants of either kind, and `jaw_grant_permissions` refuses before it opens a wallet link once it does. A new budget does not count the current one it replaces, so a connection at the cap can still renew its budget and holds one grant more until the older budget's revoke lands; a replaced budget left approved counts, and the server retries its revoke before refusing. Payments, quotes, swaps and refills draw from the newest x402 budget only, never from one it replaced or from a custom grant: when the owner revokes or changes that budget in the wallet, payments refuse `grant_revoked` and `jaw_session_status` and `jaw_session_x402_quote` answer not ready with the same reason, each pointing at `jaw_grant_permissions` for a new budget. A new x402 budget replaces the current one: once the owner approves it, the server revokes the older budget on chain as its spender, with the fee from the payer, and leaves the float in place, so once that revoke lands the connection holds one live daily USDC allowance. Migration 0034 marks replaced every budget but the newest on connections that held several before this rule, and their next tool call revokes them. A refill under the replaced budget is refused, and a payment signed under it can still be resent, since the proof spends the float and not the budget. When the payer cannot pay the fee, payments are paused, a payment holds the float or a refill is still landing, the older budget stays approved on chain but marked replaced, so nothing pays from it; `jaw_connections` lists it as `replaced` for `jaw_revoke_permission`. Any later tool call from the connection retries the revoke in the background, at most every five minutes, since only a request carries the session key; the next approval and `jaw_session_disconnect` retry it too. The revoke runs once the owner's wallet page has closed. A custom grant stays approved until it expires or `jaw_session_disconnect` revokes every live grant of the connection with the float return. The link reply tells the owner what the connection's live grants already let the session key move, summed per token and period. Other contract calls stay outside the budget. `jaw_send_calls` asks the owner to approve up to 10 calls on one chain: it returns a wallet link, and the owner reviews and signs them in the wallet and pays the gas. `jaw_get_calls_status` follows the request until it is mined. `jaw_sign` asks the owner to sign a message (EIP-191) or EIP-712 typed data: it returns a wallet link, and `jaw_get_sign_status` with its `id` (or the same call with the same `idempotencyKey`) returns the signature once the owner approves, for 7 days after the request ends. The status tools take `waitSeconds`, up to 45: the call rereads the request every 2 seconds and answers as soon as it moves, or when the time is up, sending progress notifications every 2 seconds when the request carries a `progressToken`. The time counts from the start of the call, and the wait ends early when the HTTP request does. A wait holds no database connection between reads. Past 50 polling waits in a process, or 2 for one tool on one connection, a wait reads once at the end instead. The link summaries tell the agent to call the status tool with `waitSeconds` 30 right after showing the link, and again until `approveBy`, without waiting for the owner to say they approved; later status answers ask for another wait without asking the agent to show the link again. `jaw_grant_permissions` returns an `id` beside the link, and `jaw_get_grant_status` with it answers `awaiting_owner`, `approved` with the `permissionId` in force, `owner_declined`, `expired` or `failed`. An `expired` request with `refusal.code` `link_lost`, or a `failed` one with a `permissionId`, may have left a permission in force on chain that the server never recorded: the summary of a `failed` one names its `permissionId` for `jaw_revoke_permission`, and a `link_lost` one says to revoke it by the id the wallet shows. Revoke summaries tell it to check `jaw_connections` on its own. `jaw_add_funds` returns a wallet link that shows the owner the Add Funds screen (`wallet_addFunds`) on one chain: the address and a QR code that takes any token, with no fiat on-ramp. The chain is the connection's unless `chainId` names another that `wallet_getCapabilities` lists for the account, as `jaw_get_capabilities` reads it: mainnets only on a mainnet server, testnets too on a testnet one. Any other id is refused as `unsupported_chain`, and a lookup that fails as `proxy_error`, naming the address on the connection's chain. The connection's own chain needs no lookup. Beside the link it returns the address and its chain, so funds can be sent without the wallet, and the `rate_limited` and `wallet_busy` refusals name them too. Asking again while the link waits returns the same link. A connection waits on one Add Funds link at a time, so asking for another chain meanwhile is refused as `add_funds_in_progress`, naming the waiting link and its chain. Ended Add Funds requests are deleted 7 days after they end, like sign requests. The wallet answers the same whether the owner sent funds or only closed the screen, so the request ends approved either way and the summary tells the agent to read the balance with `jaw_get_assets` on that chain right away, telling the owner the funds arrived only when the balance covers what was missing or grew past one it read there earlier, and again on the owner's next messages. A link on a testnet other than the connection's, which `jaw_get_assets` does not read, tells the agent not to check it. With no `chainIds`, `jaw_get_assets` reads the connection's chain first when it is a mainnet, then Ethereum, OP Mainnet, Gnosis, BNB Smart Chain, Unichain, Polygon, Soneium Mainnet, Base, Arbitrum One, Celo, Avalanche, Linea Mainnet, Ink, Robinhood Chain, Arc and Monad; the other supported mainnets are read only when named, and its summary names them as not checked. `jaw_resolve_name` shows a reverse name only when it is already normalized and has no control or bidi characters. `jaw_get_capabilities` still lists every supported mainnet. A `wallet_sendCalls` answer with no calls id is logged as `wallet_answer_unreadable`, and the request stays at `send_started`, since the wallet may have sent the calls. A connection waits on one sign link at a time. A session key never signs for the account.

`jaw_read_contracts` batches view-function reads (up to 100) on any chain JAW supports, through the JAW RPC proxy, and returns each decoded value or its own error.

`jaw_simulate_calls` dry-runs up to 32 calls through the proxy's `wallet_simulateCalls` and answers `success`, `reverted` (with the `callIndex` when a call is at fault) or `error`, which means the simulation could not decide and is not a failure of the calls. It takes an optional `sender` (the connected account by default), an explicit `permissionId` that is never filled in from the connection's grants, and a `paymaster`. It makes one request with no retries and signs and sends nothing.

`jaw_session_execute` sends up to 10 calls as the session key under a custom grant, by its `permissionId`, with no prompt to the owner, on a connection granted `x402:pay`. Before any userOp it checks every call's target and function against the grant, the `0x3232...3232` and `0x32323232` wildcards included, then reads from the chain whether the grant still stands and what each spend limit has left this period, less what earlier runs still open hold. It refuses by name: `call-not-allowed`, `over-limit`, `expired` or `no-grant`, and the x402 budget is refused as `no-grant` since it pays x402 services only. An `approve` or `transferFrom` on a contract the grant sets no limit on is left to the chain, since the manager skips those on an ERC-721. The same names come back when the permission manager refuses a batch that passed those checks, read from the revert data of a failed simulation or from the EntryPoint's revert log. A run takes the connection's float lock while it is checked, recorded and submitted, and its rows count against later runs until they settle, so of two runs that together pass a limit the second refuses. Ending the connection, by `jaw_session_disconnect` or by the client's revoke, waits for a run that recorded its rows and has not submitted yet, and a run whose connection ended before its record sends nothing. The end waits at most two minutes after the record, and a submit still running after one minute is answered as possibly sent, and its userOp hash is recorded on the open rows if it answers later. A send whose answer was lost on the way back is reported as possibly sent and keeps its rows open. Each run is a row in `sends` per token it moves, under its `idempotencyKey`: the same key with the same calls returns that run's outcome and never sends twice, and the same key with other calls is refused as `idempotency_conflict`. A key never runs twice: after a run that sent nothing, a new key sends again. `jaw_session_history` lists the rows with their userOp hash, paged on their own cursor, `executesBefore`, and the reconciler settles a run that got no receipt in time by that hash alone, since refills and other runs share its sender. Before anything else, a run settles this connection's open runs under its grant whose userOp the EntryPoint already logged, reading for at most 2 seconds, so a run that landed counts once, in the chain's period spend, and its key replays it landed. The grant is then read from the chain at the block those logs were read to, so a node behind it fails the read instead of answering without the run. A run that landed in the last ten minutes and that those logs do not show still counts against the grant, since the read may not have it yet. `jaw_session_status` counts what is left the same way. A run whose answer was lost has no hash, so the reconciler never marks it landed and releases it once its block window passes. A released run keeps the transaction it reverted in, so its key replays a revert apart from a run never seen on chain. The fee comes from the session key's USDC, which an x402 budget funds, and `payments_paused` stops it before anything is sent.

`jaw_session_x402_discover` searches the x402 Bazaar for services payable on the connection's chain, as the CLI's does. `jaw_resolve_name` takes an ENS name or an address and returns the other side through JAW's ENS backend, so offchain names such as JustaName subnames resolve. A name answers its address on every chain it has one for, with the Ethereum mainnet one as `address`. An address answers with its primary name only when that name resolves back to it. When nothing comes back it names a reason.

## Run it

```bash
docker build -f apps/mcp/Dockerfile -t jaw-mcp .   # from the repository root
docker run -p 3000:3000 -e DATABASE_URL=... -e JAW_MCP_PUBLIC_URL=http://localhost:3000 \
  -e JAW_KEYS_URL=https://keys.jaw.id -e JAW_MCP_SEALING_KEYS=... jaw-mcp
```

Migrations run at start and are safe to run from several instances at once.

Migrations must run as the app role, over a direct connection to Postgres, not through a transaction-mode pooler such as PgBouncer or the Supabase pooler on port 6543. Migration `0011` sets `statement_timeout` for the current role in the current database, so a different role leaves the app database unbounded. The runner also relies on session state, `set statement_timeout = 0` and `pg_advisory_lock`, which a transaction-mode pooler can move to another backend between statements, so the lock and the timeout reset stop holding. `GET /api/health` answers `{ db, paused }`, and 503 when Postgres is unreachable.

Each instance opens up to 26 Postgres sessions: a pool of 10 for requests, plus one session per refill or disconnect in progress, at most 16, which holds that connection's funding lock while it waits on the chain. Size `max_connections`, or the pooler in front of Postgres, for 26 per instance.

## Tests

`bunx nx test @jaw-mono/mcp` runs on PGlite, which runs one transaction at a time, so it cannot show a lock race. `test-pg` runs every `*.test.ts` file under `src` that references `TEST_PG_URL` (`beforeAll(TEST_PG_URL ? useTestPostgres : useTestDb)`), so a new file opts in by importing it on a real Postgres, one fresh database per file, plus the tests under `describe.skipIf(!TEST_PG_URL)`. CI runs it against a `postgres:17` service. Locally:

```bash
docker run -d --rm --name mcp-test-pg -e POSTGRES_PASSWORD=pg -p 55432:5432 postgres:17
MCP_TEST_DATABASE_URL=postgres://postgres:pg@127.0.0.1:55432/postgres bunx nx run @jaw-mono/mcp:test-pg
```

A killed run can leave `mcp_test_*` databases behind. List them with `psql "$MCP_TEST_DATABASE_URL" -c '\l mcp_test_*'` and drop each with `drop database <name> with (force)`. Removing the container removes them all.

A connection's expiry slides forward by 30 days on every successful token refresh, so a client in active use never hits the cliff. A client that stops refreshing expires after 30 days of inactivity. `jaw_session_status` includes `connectionExpiresAt` and warns the agent when the connection is within 48 hours of expiry, so it can call `jaw_session_disconnect` to sweep the float and revoke budgets while it still holds a working token. When a reused refresh token triggers revocation and its key wrap is still present (before the periodic sweep), the server recovers the key and sweeps the float before ending the connection.

To rotate sealing keys, put the new key first. A connection moves to the new key on its next token refresh, so keep the old key for at least 30 days (the maximum idle lifetime) before dropping it; `select split_part(key_wrap, '.', 2), count(*) from oauth_payloads where model = 'RefreshToken' and consumed_at is null group by 1` shows which keys are still in use. A refresh that needs a dropped key fails without using up the token, so restoring the key repairs it. Generate a key with `openssl rand -base64 32 | tr '+/' '-_' | tr -d '='`.

## Operations

The kill switch stops `/mcp`, OAuth and the interaction routes with a 503 and leaves health up:

```sql
insert into settings (key, value) values ('paused', 'true')
on conflict (key) do update set value = excluded.value, updated_at = now();
```

Payments alone stop with `('payments_paused', 'true')` in the same table: `jaw_session_x402_pay` refuses with `payments_paused` before it signs anything, `jaw_swap` keeps working since its quote is not paid, `jaw_send_calls` refuses before it opens a wallet link (a retry whose link is still live answers from the stored request), `jaw_get_calls_status` keeps working, `jaw_session_disconnect` refuses before it revokes or returns anything, and every other tool keeps working.

`/api/cron/reconcile` (GET or POST, `Authorization: Bearer <JAW_MCP_CRON_SECRET>`) clears the key wraps of refresh tokens used more than a minute ago, settles or fails every payment left `signed` or `unknown` for more than a minute by asking the chain, logs one error per payment still unanswered an hour past its deadline, ends grant, revoke, `jaw_sign` and Add Funds links no process has renewed for over 90 seconds (`link_lost` when the owner was already asked, `session_lost` when not, no code past the window; an asked revoke is left until its window ends, since other connections wait on it, unless its own connection asks again), reads the chain again for up to 50 revokes left `unconfirmed`, each at most every five minutes, and marks them revoked once it shows them (a revoke still not on chain a day after it was asked ends `failed` with `revoke_not_seen`, and is settled if a later `jaw_revoke_permission` for it finds it revoked on chain), concludes up to 50 `jaw_send_calls` requests left `sent` for more than a minute as `landed` or `reverted` by reading the bundler receipt (a request still at `send_started` has no calls id to read and is left alone; the bundler answers only for recent user operations, so one it has no receipt for ten minutes after the send is looked up on chain instead, as the `UserOperationEvent` of EntryPoint 0.8 for its calls id, in ranges of 200 blocks (the cap of the public Base RPC) and at most 50 ranges per request, for at most 5 requests per run and none once the head is 10,000 blocks past where the search starts, from the head recorded when it was sent or, for older rows, from a block estimated from the row's age; `jaw_get_calls_status` does the same), and deletes expired OAuth state, rate limit windows, audit events older than 90 days, `jaw_sign` requests (with their signatures) and Add Funds requests 7 days after they ended, and pending connections nothing refers to. Last, it reads up to 25 live grants on chain, picked at random, one at a time, and records as revoked the ones the owner revoked in the wallet instead of through `jaw_revoke_permission`. The report counts the grants it newly recorded in `grantsRevoked`, which is `null` when the store failed or three reads in a row failed, which reads as a chain outage and stops the sweep. A single grant it cannot read is skipped. A pending connection the owner approved but whose authorization never completed is retired past the interaction's end: its key revokes the budget and returns the prefund to the owner, as `jaw_session_disconnect` does, and then its sealed key is cleared. A run that cannot send keeps the key for the next one. `/api/metrics` serves payments by state, the reconciler backlog, refused `/mcp` calls per client, and `jaw_mcp_wraps_past_window`, the key wraps still stored for refresh tokens past their retry window, in Prometheus text. Each rotation sweeps those wraps and logs `wrap sweep failed` when it cannot; alert when the gauge stays above zero for longer than one cron interval.

Every tool call writes one row to `audit_events` with the connection, the tool, the outcome, and the request id from `x-request-id`. The outcome is `ok`, `error`, the code of a payment that ended without paying (such as `budget_exhausted` or `payments_paused`), or `unknown` for a payment that may have reached the seller while the chain settles it. Arguments and results are never stored. `jaw_connections` lists every connection of the account with the grants it holds by `permissionId`: kind, spend limits, expiry, and whether each is live, replaced, expired or revoked. `jaw_revoke_permission` asks the owner to revoke one permission on chain with `wallet_revokePermissions`, which the wallet renders from JAW's permission store and the owner pays the gas for. It takes any permission granted from the account: this connection's, another connection's, or one approved on chain that this server never recorded, which it reads from the same store. The tool refuses an unknown id, a chain the permission was not granted on, a permission already revoked or ended, and a recorded grant the store does not hold, before any link opens. A connection gets 10 revoke requests a minute for permissions with no revoke link waiting; the next is refused as `rate_limited` before the permission store or the chain is read. Asking again about a permission whose revoke link waits is not counted. One connection waits on one revoke at a time, and a permission has one revoke link across the account; unique indexes on `permission_requests` hold both. Once the chain shows it revoked, the `grants` row is marked revoked. A grant the wallet answered but the server did not record keeps its id on the request row, and `jaw_connections` lists it under `unrecorded` until a revoke of it is confirmed on chain. Grant, revoke and `jaw_sign` links are rows in `permission_requests` and count toward the account's three open links with `jaw_send_calls` and `jaw_swap`. Add Funds links do not, since they move no funds, so a waiting one never makes another request `account_busy`. They hold owner sessions all the same, so an account waits on at most 2 Add Funds links across its connections, the 5 sessions an address may hold less the three open links, and the next is refused as `add_funds_busy`, still naming the address and its chain but not the other connections' links. A row whose process has not renewed its 30 second lease for a further minute no longer counts. That minute is there for a database stall: until it passes, nothing closes the link, and the process that holds it can still ask the owner once the database answers. The relay drops what the wallet sends while no process listens on its link, so a restarted server cannot hear an answer given there. If that session had not asked the wallet yet, the next request for the same thing marks the row expired with `session_lost` and opens a new link. If it had, or if the relay session dropped after asking, the row ends expired with `link_lost`. `jaw_sign` answers `link_lost` for that key. The next new link of the same kind (grant, revoke or sign) from the same connection names the lost one, and only that link does: its replies, retries included, carry the warning while the owner could still approve the old link, so the agent can tell the owner not to. Once a link is `link_lost` the owner holds two links for the same kind of request. The server never hears an answer on the old one, but a grant or revoke the owner approves there still happens on chain, which is why the warning asks the owner not to. A database stall of more than 90 seconds is the one case where the server can hear both: the old process keeps its socket, and an answer the owner gives there still settles the old row, even after the row was closed, until its first lease renewal that the database answers finds the row closed and drops the socket. That is within 10 seconds of the database answering again. After a real restart no process listens on the old link, and the relay drops what the wallet sends there. A connection never closes another connection's asked revoke before its window ends: a revoke of the same permission from another connection gets `revoke_in_progress` while that link is live or asked, even after its lease lapsed. A link whose lease lapsed before it asked the owner can never ask, so any connection may close it as `session_lost`. Before asking the wallet, a session claims its row while the lease holds, so a session that lost its row never asks. `jaw_session_disconnect`, called from the connection itself, also revokes its budgets on chain and returns the float to the owner first. When the payer's balance is too low to cover both the fee and a sweep, a revoke-only batch sends the revocations and lets the paymaster take its fee from whatever is there; the remainder stays in the payer. A grant whose state the chain does not return is left out of the batch and listed in `unread`, and the rest still revoke and sweep.

Authenticated `/mcp` calls get 120 requests per minute per connection, and unauthenticated routes 120 per client IP, counted in Postgres. Behind your own proxy, production must set `JAW_MCP_TRUSTED_PROXY_HOPS`: without it the client IP comes only from `x-real-ip` (which Vercel sets), and with neither the per-IP limit is skipped rather than shared, with a warning at start.
